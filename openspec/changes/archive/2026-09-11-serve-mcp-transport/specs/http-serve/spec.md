# http-serve Specification (delta)

## Purpose

Loopback Streamable HTTP transport for the codeindex MCP server so multiple
hosts can share one process-level watcher, scheduler, and freshness state
instead of each spawning a competing stdio writer against the same worktree
database.

## ADDED Requirements

### Requirement: Loopback Streamable HTTP MCP endpoint

The system SHALL expose a Streamable HTTP MCP endpoint bound to `127.0.0.1`
that serves the same tools and handlers as the stdio transport (`code_search`,
`code_symbol`, `code_impact`, `code_index`). The default port SHALL be `3456`;
the CLI SHALL accept `--port <n>` to override. Non-`/mcp` request paths SHALL
return `404`.

#### Scenario: Client completes a tool call over HTTP

- **WHEN** a Streamable HTTP MCP client initializes against `http://127.0.0.1:<port>/mcp` and invokes `code_search`
- **THEN** the response carries the same text summary and `structuredContent` shape as the equivalent stdio call (including `matchedBy`, `preview` default, and freshness fields)

#### Scenario: Default port is used when unspecified

- **WHEN** `codeindex serve` is started without `--port`
- **THEN** the server binds `127.0.0.1:3456`

#### Scenario: Port already in use fails clearly

- **WHEN** `codeindex serve` cannot bind because another process holds the port
- **THEN** the process exits non-zero with a message that names the configured `repoRoot` and suggests `--port`

### Requirement: Shared process session model

HTTP serving SHALL run one MCP session assembly path with stdio: one reindex
scheduler, one watcher, and one freshness-state provider for the process.
Multiple concurrent HTTP clients SHALL share that single writer rather than
each constructing an independent scheduler or watcher.

#### Scenario: Concurrent clients share one writer

- **WHEN** two HTTP clients invoke `code_index` (or one invokes `code_index` while a watcher catch-up is active) on the same serve process
- **THEN** the runs serialize through the existing single reindex queue and at most one follow-up coalesces

### Requirement: Stateful MCP sessions

The HTTP transport SHALL use stateful session management with a
`mcp-session-id` header generated by the server. Invalid or unknown session
ids on non-initialization requests SHALL be rejected according to the
Streamable HTTP transport rules.

#### Scenario: Initialization establishes a session id

- **WHEN** a client completes MCP initialization over Streamable HTTP
- **THEN** the server returns a session id that subsequent tool calls present on the `mcp-session-id` header

### Requirement: Optional bearer authentication

Bearer authentication SHALL be optional and disabled by default (loopback
trust). When a token is configured (env var or token-file path), every HTTP
request SHALL require `Authorization: Bearer <token>`. Comparison SHALL be
constant-time. Failed authentication SHALL return `401` with
`WWW-Authenticate: Bearer`. The configured token MUST be at least 32
characters. Stdio transport SHALL NOT require a bearer token.

#### Scenario: Auth disabled by default

- **WHEN** `codeindex serve` starts with no token configured
- **THEN** MCP clients connect and call tools without an `Authorization` header

#### Scenario: Wrong token is rejected

- **WHEN** a token is configured and a request presents a missing or incorrect bearer token
- **THEN** the server returns `401` with `WWW-Authenticate: Bearer` and does not execute the tool

#### Scenario: Correct token is accepted

- **WHEN** a token is configured and a request presents the matching bearer token
- **THEN** the tool executes and returns the normal MCP tool result

### Requirement: Protocol boundary coverage for both transports

The change SHALL include tests that drive a real MCP `Client` over both
`StdioClientTransport` (spawning the stdio server process) and the Streamable
HTTP client transport, covering at least `listTools` and one tool call each,
plus bearer accept/reject paths over HTTP.

#### Scenario: Stdio client round-trip

- **WHEN** a test spawns `codeindex mcp` as a child process and connects `Client` + `StdioClientTransport`
- **THEN** `listTools` includes the four codeindex tools and `code_search` returns a structured payload

#### Scenario: HTTP client round-trip

- **WHEN** a test connects `Client` + Streamable HTTP client transport to a live `serve` endpoint
- **THEN** `listTools` and `code_search` succeed with the same tool surface as stdio

#### Scenario: Graceful shutdown

- **WHEN** the serve process receives SIGINT or an explicit stop
- **THEN** the watcher stops, open transports close, and the process exits without leaving the HTTP port bound
